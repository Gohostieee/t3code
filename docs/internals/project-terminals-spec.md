# Project terminals that follow the checkout

## Problem Statement

Terminal sessions currently belong to a thread. Users working on one project across several threads must remember which conversation owns their shell, dev server, and terminal history. Opening a terminal in another thread creates a different working environment even when both threads use the same checkout. Archiving or deleting the owning thread can stop those terminals.

A single indiscriminate terminal for the whole project would introduce another problem: threads can run in different Git worktrees, and a shell must not silently change directory or restart when the user switches conversations. Thread branch metadata can also differ from the branch actually checked out on disk. Sharing by project name, repository URL, or branch name would send users to the wrong workspace.

Users need a project terminal that is shared wherever the underlying checkout is the same, remains separate wherever execution must be isolated, and clearly shows the workspace it controls.

## Solution

Provide one default interactive terminal per project checkout in an environment. All threads using that checkout open the same shell, history, and running process. A project with only its main checkout therefore has one default terminal. Each separate worktree has its own default terminal. Additional terminals and splits remain available for independent commands.

The normal terminal action follows the active thread's resolved checkout. A project-level terminal action works without creating or selecting a thread and opens the main checkout by default, with a chooser for the project's existing worktrees. Returning to a checkout reconnects to its existing terminal. Navigation alone never sends shell input, performs a Git checkout, changes a shell's directory, or restarts a process.

The terminal shows the project, checkout location, and actual current branch or detached HEAD when Git information is available. The branch is a description of that directory's current state, not the identity of the terminal. If the user changes branches in place, the same terminal remains attached and its checkout label updates. Separate terminals cannot provide separate branches inside the same physical working directory; that requires separate worktrees or clones.

Sharing decisions:

| Situation                                                                                                  | Behavior                                                                                                                              |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Two threads in the same project and main checkout                                                          | Share the default terminal.                                                                                                           |
| Two threads in the same existing worktree                                                                  | Share that worktree's default terminal, including when one thread was forked from the other.                                          |
| Main checkout and a linked worktree                                                                        | Separate terminal groups.                                                                                                             |
| Two different worktrees, even at the same commit or with similar branch labels                             | Separate terminal groups.                                                                                                             |
| Branch switch, branch rename, commit, reset, or detached HEAD in the same checkout                         | Keep the terminal; refresh the checkout description. Do not restart running commands.                                                 |
| Different recorded thread branches but the same actual checkout directory                                  | Share the terminal and show disk state; do not pretend the threads have isolated branches.                                            |
| Another clone of the same repository                                                                       | Separate checkout and terminals.                                                                                                      |
| Different projects with matching names, remote URLs, overlapping roots, or the same path                   | Keep project ownership separate. Separate shell ownership does not imply filesystem isolation.                                        |
| Another environment, including a second T3 server on the same host                                         | Separate terminals.                                                                                                                   |
| Same environment reached through local access, SSH forwarding, relay, or a tunnel                          | Reattach to the same server session after environment identity is resolved. Transport is not ownership.                               |
| Web, desktop, mobile, multiple tabs, or multiple devices attached to the same environment/project/checkout | Share the server session; keep view layout and focus local to each client.                                                            |
| Bottom drawer, side panel, command palette, or terminal keybinding                                         | Resolve the same checkout and terminal identity. Moving the view does not create another shell.                                       |
| Project with no threads, or an unsent draft using an existing checkout                                     | Open the checkout's terminal without creating a synthetic thread.                                                                     |
| Draft requesting a worktree that has not been provisioned                                                  | Show that the requested checkout is not ready. Do not silently open the main checkout or create a worktree merely to show a terminal. |
| Subdirectories within the same project checkout                                                            | Retain the same default terminal. An explicit request to launch in another directory can create an additional session there.          |
| User runs `cd`, changes shell variables, or activates a virtual environment                                | Preserve that shell state across threads; do not change its project ownership.                                                        |
| User explicitly chooses New Terminal or Split                                                              | Create an additional independent session in the selected checkout.                                                                    |
| Project script, worktree setup, or another automatic command launch                                        | Use a separate task terminal in the requested checkout, never inject into the shared interactive shell.                               |
| Different shell configuration or launch environment is explicitly requested                                | Use another session, or an explicit restart chosen by the user; never repurpose a running session on attachment.                      |
| Provider-managed agent execution or an external terminal app                                               | Retain its existing ownership. It is not the project's shared interactive terminal.                                                   |
| Missing, removed, or replaced checkout                                                                     | Report the original checkout as unavailable; never redirect the old terminal to the main checkout or a newly created directory.       |
| Non-Git project                                                                                            | Share by the project's resolved directory, without a branch label.                                                                    |

6. As a user, I want a draft for an uncreated worktree to explain that its terminal is not ready, so that I do not accidentally run commands in the main checkout.
7. As a user, I want all threads using one worktree to share its terminal, so that continuing a task in a new conversation preserves my working tools.

57. As a user, I want terminals in non-Git directories to share normally, so that this feature remains useful outside Git repositories.
58. As a user, I want hidden and inactive terminals to consume little client rendering and network work, so that project sharing does not slow down a large workspace.

## Implementation Decisions

- **Ownership follows an environment, project, and checkout.** A checkout means the resolved working directory used for execution: the project's workspace root or an existing worktree belonging to that project. Use a server-resolved checkout identity and stable session identity. A thread may supply launch context or attribution, but it is not the owner. Do not introduce a synthetic terminal thread, identify checkouts by branch or remote URL, or coalesce separate project records by path.

- **Resolve paths on the environment.** Use existing workspace and VCS services to validate and normalize checkout locations, including platform-specific path rules. Equivalent path spellings or aliases within the same project should resolve to the same verified checkout; do not lowercase paths indiscriminately on case-sensitive filesystems. A linked worktree may be outside the project's root, so membership must not be implemented as a simple path-prefix test. Preserve distinctions between separate worktrees, clones, nested repositories selected as distinct workspaces, and environments. Missing or ambiguous context is a typed error, not a reason to choose the main checkout.

- **One primary session is a default, not a hard limit.** The server atomically gets or creates the primary interactive session for a checkout. Concurrent clients cannot each allocate a different primary. Existing New Terminal and Split actions explicitly allocate additional sessions under that checkout. Session identifiers remain opaque to clients; no client-local counter can determine uniqueness across devices. Preserve existing practical split and retention limits.

- **Extend the existing terminal boundary.** Update shared terminal contracts, the server terminal manager and RPC handlers, metadata and attach streams, history storage, errors, and shared client runtime to address a session through its project/checkout owner. Keep presentation and renderer choice out of the wire model. Metadata provides the owner, launch location, session kind, lifecycle status, and primary designation without exposing environment-variable values. Reuse the current PTY orchestration and subscription model instead of adding a second terminal service or a general-purpose resource framework.

- **Opening a view and launching a process are distinct operations.** Ordinary attach and navigation never restart a session, replace its environment, clear its history, or send commands. Opening the default terminal is an explicit get-or-create action; subscribing to an explicitly closed session must not recreate it. Reject an incompatible launch request for an existing session with a clear response, or allocate an explicitly requested additional session. Change launch context only through a visible restart/new-session action. Distinguish a session generation when necessary so delayed writes, closes, or resizes cannot affect a replacement process.

- **Resolve the target before accepting input.** The shared client runtime owns checkout resolution and session targeting for web and mobile. During worktree creation, route changes, project changes, or reconciliation of draft and durable thread state, show a resolving or unavailable state until the target is known. Bind every mutation and pending launch to its captured session target; discard obsolete route results. Never let an old response or pending command borrow the newly selected thread's identity. An optimistic client layout is not proof that the server created a session.

- **Checkout state is descriptive.** Subscribe to the existing VCS status mechanism for the selected checkout. Use its actual branch or detached HEAD instead of a thread's remembered branch. Branch changes and checkpoint restoration within the same working directory do not change terminal ownership or restart commands. If a thread's expected branch disagrees with disk state, show the actual checkout and explain the mismatch where relevant. A running process may still hold state from before a branch change; the label must not imply the process was restarted. No new Git checkout policy is introduced.

- **Shell state is preserved, not inferred.** Store and label launch location separately from any trustworthy live shell directory information. A user typing `cd` or exporting variables does not transfer the session to another checkout or project. Do not inject commands to discover or repair shell state. An explicit launch from a subdirectory may create an additional session, while the checkout's primary remains unchanged. Configuration changes affect new sessions; restarting an existing one is explicit.

- **Project access and thread access converge.** Add a discoverable project terminal action and a checkout/session chooser that work without any threads. Thread terminal actions resolve the thread's actual checkout; project actions initially select the main checkout. Keep the selected session and terminal layout per client and checkout so switching threads in that checkout preserves the view. Explicit inspection of another checkout must show its location, offer Return to current checkout, and reset to following the newly selected thread on thread navigation. Apply this behavior to the bottom drawer, right panel, project/sidebar actions, command palette, terminal keybindings, mobile routes and panels, and desktop shell entry points that invoke them. Terminal appearance settings remain client preferences and do not spawn sessions.

- **Automated commands use task sessions.** Project scripts, worktree setup, and any existing provider-maintenance flow that launches a visible terminal use dedicated task sessions with the exact requested launch directory and runtime environment. Preserve project-root and worktree environment semantics. Do not treat a shell with no detected subprocess as safe for automation: it can contain partial input or changed directories. Setup remains governed by worktree provisioning and runs once for that provisioning action, not on every thread attachment. A deliberate new Run action may create another task session; reconnect or request retry must not rerun a command. Use existing command/request identity for deduplication where available, and report an unknown outcome instead of blindly replaying side effects. Task sessions and their output remain discoverable from the owning checkout and are distinguishable from the primary interactive terminal.

- **Provider execution remains separate.** Codex, Claude, Cursor, Grok, and OpenCode all get the same client terminal behavior because these are server-owned user PTYs. Their adapters' private shell/tool execution, provider sessions, approvals, and execution environments remain unchanged. Provider selection is not part of the shared terminal key. Any existing integration that explicitly creates a visible user terminal must pass the resolved checkout and task ownership; no adapter receives implicit access to inject commands into the primary shell. Container, WSL, or alternate-user execution is not added here; any already-supported distinct execution environment must remain distinct.

- **Shared session, independent views.** Authorized clients attach to the same PTY and see the same bytes and lifecycle changes. Retain existing terminal permissions and direct input semantics: this is a shared writable shell, not simultaneous-input conflict resolution. Keep layout, focus, font settings, viewport scroll position, and temporary selections local. Within one client, moving a session between drawer and panel transfers presentation rather than launching another PTY or duplicating keystrokes. Resize only from a visible, focused view; passive replay and background layout must not continuously resize the PTY. If multiple clients actively resize, the last accepted foreground resize wins, without resize-echo loops. A new collaborative editor, controller lease, or session broker is not needed for this feature.

- **Thread cleanup no longer owns shared sessions.** Remove project-owned terminal termination and history deletion from thread archive/delete handling and thread UI retention cleanup. Provider sessions still follow their existing thread lifecycle. Project terminal access remains available after every thread has been archived or deleted. Hiding a view detaches presentation only. Terminate Session, Restart Session, and Clear Output have clearly communicated session-wide effects and propagate to other clients. After termination, choose an eligible remaining interactive session as primary or lazily create one on the next explicit Open action; task terminals never become primary automatically. Use deterministic selection and preserve all unrelated sessions.

- **Checkout and project cleanup are explicit.** Integrate terminal ownership into existing worktree removal and orphan-worktree cleanup: show affected sessions, allow cancellation without side effects, and terminate only those sessions after the user proceeds. A worktree with shared terminals is not disposable merely because its last thread was deleted. Coordinate removal with new terminal opens so a new process cannot appear after the removal preflight. If removal fails, report that failure and the actual terminal state. Externally missing or detected-replaced checkouts become unavailable for new launches and writes rather than falling back; retain diagnostic history and allow termination. Once a checkout is known removed, never rebind its old sessions to a directory later created at the same path. Project root changes select a new checkout without retargeting old sessions; keep old sessions visibly labeled and manageable until explicitly closed. Renaming a project preserves ownership. Explicit project deletion accounts for and closes only that project's sessions and follows existing project-data retention policy; it does not imply deleting repository files.

- **Reconnect is different from server restart.** Transport changes and client reconnects reattach to the existing environment-owned session. Reuse existing environment identity resolution; do not key sessions by URL, pairing token, or connection mode. Disconnecting a client does not terminate a PTY. Retain history and session metadata under the environment's existing storage and retention model. A server shutdown still ends its PTYs: after restart show saved output as ended/restored, and require an explicit new launch or restart. Do not claim process survival across a server restart or add a terminal daemon.

- **Migrate without merging processes or histories.** Resolve existing thread-owned terminals from their recorded launch location, worktree metadata, and project association, rather than the thread's possibly changed current checkout. Preserve each mappable legacy terminal as its own session in the checkout group. Designate one compatible interactive session as primary deterministically, preferring a running eligible session and using a stable identity as a tie-breaker; retain the others as additional sessions with originating-thread labels where useful. Preserve separate transcripts and migrate local drawer/panel references to resolved session identities. Never concatenate histories, kill duplicate sessions, or restart a live process merely to normalize ownership. Preserve ambiguous or unmappable history as clearly labeled legacy history rather than guessing its checkout. Make migration idempotent. Ordinary upgrade/server restart limitations still apply to live PTYs. Coordinate contract changes across clients and server; older clients must use an explicit supported compatibility path or receive a version/update error, never silently retarget a shared session through legacy thread commands.

- **Context, links, and activity follow the new owner.** Captured terminal excerpts remain immutable message context and include enough project/checkout/session provenance to disambiguate their source. They attach to the conversation the user chooses, without making that conversation the terminal owner. For terminal links requiring a thread-bound preview, use the currently consuming thread; from a project-only terminal use the existing normal link-opening behavior without inventing a thread. Project activity counts each session once. Thread indicators, if retained, describe shared checkout activity rather than claiming thread ownership. Apply existing history limits and expired-selection behavior using the new identities.

- **Keep sharing inexpensive.** Spawn lazily. Preserve the metadata/byte-stream separation, bounded history, ordered snapshot-plus-delta replay, and shared subscription lifetime. Avoid replaying history merely because the user changes threads within one checkout. Hidden surfaces release rendering work; inactive checkout lists subscribe to lightweight metadata, not every PTY's full output. Reuse VCS status subscriptions instead of running Git per render or keystroke. No continuous attention animations are added. Update shipped-product documentation for terminal ownership and lifecycle, and maintainer documentation/glossary for checkout identity and migration.

## Testing Decisions

- **Primary seam: public terminal and orchestration RPC behavior.** Extend the existing server test harness and WebSocket client helpers. Compose the real checkout resolution, terminal manager, state/history handling, and relevant lifecycle handlers/reactors, with the existing fake PTY adapter and disposable workspace fixtures underneath. The current server terminal-routing tests mock the terminal manager and prove routing only; those mocks are insufficient for this feature's sharing assertions. Keep the behavioral matrix at this one integration boundary rather than duplicating ownership tests in every UI component.

- **Test observable outcomes.** Assert returned session identity and owner, shared output, process lifetime, distinct launch locations, visible lifecycle events, and preserved transcripts. It is valid to observe fake PTY spawn/stop/write behavior because it represents the external process boundary. Do not couple tests to private maps, helper call order, or exact storage filenames. Use real temporary Git repositories/worktrees for canonical checkout and actual-branch behavior, including an external branch switch. Cover platform-appropriate path aliases and case rules without assuming every platform has the same filesystem behavior.

- **Core sharing matrix.** Exercise two threads on the main checkout, two on one worktree, main versus worktree, two different worktrees at the same commit, another clone, different projects, different environments, a non-Git project, a project without threads, and a draft with an unresolved worktree. Confirm in-place branch changes preserve the session while separate directories remain separate. Exercise explicit additional terminals and shell launch overrides without modifying the primary.

- **Concurrency and lifecycle at the same seam.** Race two default opens and prove one PTY; attach two clients and verify matching output; disconnect and reconnect one without affecting the other; close a session while a stale attachment remains and prove it is not resurrected; reject delayed mutations targeting an ended generation; archive/delete the creator and last thread without stopping shared terminals; remove a checkout with cancel/success/failure paths; race removal against an open; and verify project deletion cannot affect another project. Distinguish server restart with restored history from a live reconnect.

- **Commands, migration, and checkout changes.** Verify script/setup launches use dedicated sessions in the intended checkout, do not write into the primary shell, and do not replay after reconnect. Prove a changed launch environment cannot silently restart an attached interactive session. Cover multiple legacy terminals with separate histories, duplicate old terminal IDs from different threads, unmappable legacy locations, repeated migration, project-root changes, missing/replaced worktrees, and supported or rejected old-client contracts. The prior art is the existing terminal-manager reuse/attach/history/worktree tests, project-setup runner tests, server archive/bootstrap RPC tests, and VCS integration tests.

- **A small client layer covers presentation-only behavior.** Extend shared terminal stream/state tests and existing web terminal UI state, right-panel, cleanup, and terminal-context tests; extend mobile launch-context, route bootstrap, route-screen, and panel tests. Assert checkout selection, stale-route response suppression, local layout retention, focused resize behavior, no duplicate input handling, and accurate labels. Verify captured excerpts do not change after navigation and background views do not replay or continuously render output. Do not repeat the full server ownership matrix in each client suite.

- **Integrated client acceptance is an implementation requirement, not evidence supplied by this spec.** After integration, exercise web, desktop, and mobile with two threads sharing a checkout and a third using another worktree; keep a harmless long-running command alive through navigation and thread archive; open from the project with no selected thread; attach a second client; and verify local plus remote connection behavior. Include a mobile reconnect and terminal movement between web drawer and panel. Use isolated T3 state and disposable checkout fixtures, never a server pointed at live userdata. Browser/computer-use verification requires the developer's explicit agreement under repository policy. Collect before/after UI evidence if a PR is later requested.

- **Use existing async completion signals.** Synchronize tests with terminal events, subscription handshakes, explicit barriers, available orchestration receipts, and worker drains. Test clocks are appropriate for timeout behavior; fixed sleeps and polling until an assertion happens to pass are not. Receipts remain test infrastructure, not a production control mechanism. Run focused affected tests and scoped lint/typechecks; CI owns repository-wide checks.

## Out of Scope

- Implementing this feature as part of the specification task.
- A single shell shared across separate worktrees, projects, clones, machines, or T3 environments.
- Enforcing exactly one terminal or removing existing additional-terminal and split workflows.
- Making separate shells provide isolated branches within the same physical checkout.
- Automatically switching Git branches, creating worktrees on terminal view, or changing the user's shell directory during navigation.
- Sharing provider-private execution terminals, changing agent permissions, or giving agents implicit access to the interactive project shell.
- Replacing terminal renderers, adding new execution environments, or adding shell instrumentation solely to discover live directory state.
- Surviving an environment/server restart with live processes through a new daemon, tmux integration, or process migration.
- Collaborative input merging, per-user terminal workspaces, or a new control-lock system.
- Global terminal sharing with external terminal applications or unconnected T3 servers.
- Sharing other thread-owned surfaces such as previews, diffs, or conversation drafts.

## Further Notes

This spec interprets "one terminal per project" as one automatically shared default for each real checkout, with explicit extra sessions for independent work. A project using only its main directory gets the requested single default terminal. Worktrees are the important exception because their files and processes must stay separate.

The implementation should preserve the existing architecture: the environment owns PTYs, shared contracts carry terminal operations, the shared client runtime owns connection and domain state, and each client owns presentation. The existing terminal-renderer architecture remains applicable. No new provider dependency or terminal backend is required.

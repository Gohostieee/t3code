# Source-derived Codebase Atlas MVP

Date: **2026-10-27**. Status: **testing boundary approved; publication pending tracker setup**. This is a specification, not an implementation or acceptance report. It defines a replacement direction for the Codebase explorer while preserving existing accepted AI maps as legacy documentation.

## Problem Statement

The current Codebase explorer asks an AI to author architecture graphs. A source citation can show where an explanation came from without proving that the depicted relationship exists. Exploring the whole project takes repeated provider work, and the result depends on an AI's choice of scopes and descriptions. Users cannot immediately rely on it as an inventory of routes, components, and connections in the checkout they are editing.

Users want to open a project and see its actual structure as navigable visual blocks. For a web application, they also want to recognize the screens: which routes exist, what wraps each page, which components it uses, and what those pages look like with representative data. A file tree alone does not answer these questions. A generated description or a diagram that looks authoritative but guesses relationships does not answer them reliably either.

The first release must deliver a complete useful workflow: index a supported application without AI, browse its source-derived map, organize routes into features, attach a running app, capture named page scenarios, and return after an edit or reconnect without losing the accepted map. It must remain usable from web, desktop, and mobile clients connected to a local or remote environment.

## Solution

Make **Codebase** a source-derived atlas. Its structure comes from parsed source and explicit framework rules. Its page thumbnails come from actual browser captures of an attached application. Its feature groups come from the user. These three kinds of information remain distinguishable throughout the interface.

The user selects an environment, project, checkout, and application root, then explicitly chooses **Index codebase**. No provider selection, credentials, analysis thread, application execution, or browser is needed for indexing. The accepted result opens as an application overview with Routes, Modules, Features, and Files views. Selecting a route reveals its layout and boundary composition, directly identifiable component uses, module dependencies, endpoint declarations where applicable, and source references. Deeper detail loads on demand.

The user can create feature groups such as “Projects” or “Billing” and attach routes or source items. Feature groups are documentation authored by the user; the application does not claim to infer business capabilities from import names.

To see a page, the user attaches an application that is already running in the selected environment and saves a named scenario. A scenario supplies concrete route parameters, optional query values, a viewport, an optional private session profile, and an observable readiness condition. **Capture** produces a thumbnail and an inspectable screenshot for that scenario. Static routes can receive a default scenario draft; dynamic parameters are never invented. Each capture shows its time, outcome, target, and relationship to the indexed source snapshot.

**MVP release boundary:** ship source indexing for the Next.js App Router and the TanStack file-routing configuration used by T3; a generic JS/TS module and file view; user-authored feature groups; and explicit page captures from an attached app. The first release includes all four capabilities. A parser-only graph or mocked thumbnails do not satisfy this spec.

## Implementation Decisions

### 1. Product scope and vocabulary

- Reuse the existing Codebase destination and its entry-point resolver. Sidebar entry, entry from Chat, the command palette, and the configured keybinding must resolve the same environment/project/checkout state. Settings may expose preferences or a link; it must not host a separate explorer implementation.
- Introduce **atlas** for accepted source-derived structure, **index job** for deterministic extraction, **scenario** for a named concrete rendering setup, and **capture** for one runtime observation. Retain **pass** for legacy provider analysis. A parser job is not an agent turn and does not create a conversation thread.
- Present Routes, Modules, Features, and Files as views of the same accepted atlas. Use one compact toolbar and progressive disclosure for inspection, configuration, activity, and diagnostics. Preserve selection, scroll position, and breadcrumbs across dialogs and view changes.
- Index the selected project's eligible inventory, but provide framework-specific routes for one selected application root per atlas in the MVP. Application selection never combines URL spaces. Shared workspace modules may appear as dependencies of that application. Other applications remain accounted for in the inventory and can be selected explicitly for their own atlas.
- User-authored feature groups have a stable ID, name, optional description, and references to route/module/component IDs. Support create, edit, delete, assignment, unassignment, filtering, and an ungrouped view. Do not introduce free-form graph authoring or automatic business-feature inference.

### 2. Source extraction and adapter support

- Place source extraction behind a server-owned read-only extractor boundary. Reuse checkout resolution, inventory, fingerprints, source previews, and bounded file handling from the existing Codebase services. Implement compiler parsing and module resolution rather than extending the token-based import matcher into a pseudo-parser.
- Use a pinned TypeScript compiler API for JS, JSX, TS, and TSX source. The initial implementation uses the established classic API through a contained adapter, not a wholesale compiler migration. Keep the installed native compiler used by contributor tooling unchanged. Unsupported syntax produces a diagnostic and inventory status, not fabricated facts.
- Read effective compiler configuration, project references, package exports, and workspace context for module resolution. Preserve import kind and resolution provenance. Do not execute project configuration, plugins, generators, builds, or arbitrary source during indexing. Recognize literal configuration only through documented adapter rules; expose values that require execution as unknown.
- Extract modules, exported declarations, resolved import/re-export edges, and directly resolvable JSX component-use edges. Resolve aliases and simple local wrappers when the compiler establishes the target. Dynamic registries, computed imports, unresolved higher-order wrappers, and unavailable dependencies remain explicit unresolved references. Imported type declarations are not runtime components.
- Distinguish at least **declares**, **imports**, **re-exports**, **type-dependency**, **JSX uses**, **route entry**, **layout wraps**, and **boundary applies**. Each extracted relationship has source coordinates, a normalized source fingerprint, extractor/rule version, and an evidence kind: syntax, symbol resolution, or framework rule. These establish source facts, not runtime execution.
- The Next adapter initially targets App Router conventions validated against Next 16.4.x fixtures. Advertise the tested version/rule capabilities; do not imply every Next release or configuration is supported. Other detected versions may expose generic modules and explicitly partial route facts, with a reason.
- Next route facts include application-root selection, URL patterns, groups and private segments, single/catch-all/optional parameters, nested and multiple-root layouts, template roles, loading/error/global-error/not-found boundaries, endpoint declarations and exported HTTP methods. Record server/client directives accurately as source declarations; do not claim that a local directive alone proves the entire runtime component classification.
- Identify named slots, default fallbacks, and intercepted-route declarations and their resolvable target references. Preserve their special composition and navigation requirements. Normal hard-navigation capture is supported; generic soft-navigation/modal-state replay is outside the MVP. Show that missing scenario coverage explicitly rather than calling one hard-navigation image exhaustive.
- Identify proxy/middleware, routing configuration, deployment prefixes, localization, and rewrite/redirect declarations when supported by literal rules. Computed outcomes remain unknown. Unknown configuration affecting URL construction requires a user-supplied preview prefix or relative path and prevents a complete routing claim.
- The TanStack adapter must support the file-routing conventions and plugin configuration used by T3: route declarations, index and dynamic parameters, pathless parents, nesting, and statically identifiable route components and boundary roles. Cross-check generated route output when available, but do not trust an unvalidated generated tree over current declarations. Mark computed route options and unsupported conventions explicitly.
- Next Pages Router, code-defined TanStack route construction beyond supported declarations, and other frameworks get inventory and generic JS/TS views with clear missing route support. Keep legacy maps available for them. They are not release blockers for this MVP, and the new atlas must not claim a complete route catalog for them.
- Do not add a general call graph, endpoint-to-database graph, runtime request inference, or rendered DOM-to-component mapping. Endpoint discovery is useful on its own. A module import never becomes a call edge, and a browser screenshot never becomes proof of a React component identity.

### 3. Determinism, coverage, and accepted artifacts

- Define versioned portable contracts for atlas manifests, bounded structure documents, evidence, diagnostics, feature groups, and scenario definitions. The schema separates extracted facts, user-authored documentation, and local runtime observations. Analyzer provenance is not required for an atlas.
- Keep portable artifacts within the selected project's existing Git-owned Codebase namespace, separated from the legacy schema. Use app-relative semantic identities that include the owning application and qualified source identity, excluding machine paths, timestamps, and line numbers. Renames may produce new IDs. Preserve unresolved user references visibly rather than guessing a rename correspondence.
- Identical source, effective configuration, extractor versions, and user documentation produce byte-identical structural artifacts and stable IDs across scans and clones. Keep run timestamps, physical checkout identity, and runtime audit data outside the canonical portable structure. Normalize text line endings consistently with the existing fingerprint model.
- Publish bounded immutable structure documents through a single accepted manifest revision. Reuse the checkout lock and expected-revision/source rechecks; the manifest switch is the acceptance boundary. Do not assume several independent file replacements form a filesystem transaction. Reject detected source, branch, configuration, parent, or destination conflicts and leave the last accepted generation intact.
- Use the existing source policy as the starting point: 20,000 inventoried files, 1 MiB per retained parsable source file, 80 nodes/200 edges in a graph view, 512 KiB per structure document, 50 rows per list page, and a 32 MiB structural generation budget. These are proposed release limits, not measured capacity claims. Reaching a processing or generation limit produces explicit partial status and omitted counts. Bound discovery itself; never silently ignore overflow beyond a scan limit.
- Separate inventory accounting, parse coverage, module resolution coverage, framework-rule coverage, and preview-scenario coverage. Parsed lines do not prove runtime coverage, and accepted legacy AI ranges do not count as parser coverage. Binary, generated, oversized, ignored/private, unsupported, and failed-to-parse inputs have distinct policy or diagnostic treatment. Excluded private paths do not expose secrets through the inventory.
- Reuse per-file syntax results when content and parser inputs match. Re-resolve affected dependencies conservatively; configuration, framework-version, workspace, or lockfile changes may invalidate the whole application. Do work away from latency-sensitive request handling. Watch notifications invalidate cached assumptions; a watcher event or matching commit alone never establishes freshness.
- A source edit marks the relevant atlas snapshot stale until explicitly refreshed. The previous atlas remains navigable with its revision and stale state. Opening a view may validate freshness, but does not publish a new generation, run a provider, start an app, or capture pages.
- Save feature/scenario documentation with expected-revision protection independently of regenerated structure. Regeneration preserves these records. A deleted route leaves a visible missing reference and disables its capture until repaired or removed. Explicit metadata changes may write portable documentation; navigation never does.

### 4. Index job lifecycle and contracts

- Extend the existing typed Codebase service and shared client state with operations for capabilities/application discovery, starting and reading an index job, reading paged atlas views, subscribing to compact revisions/progress, cancellation, and editing user documentation. Keep legacy reads distinguishable rather than decoding both formats as one undifferentiated graph.
- A new index command carries a command ID, project/checkout/application binding, expected accepted revision, and supported options. It does not carry a provider model. Reusing a command ID with changed input is a conflict. At most one index publication job runs per physical checkout; equivalent requests attach, while different requests queue within a bounded queue.
- Persist job identity and lifecycle in environment-local SQLite using existing persistence conventions. A job reports queued, inventorying, parsing, resolving, validating, publishing, and terminal state. Terminal states distinguish completed, partial, cancelled, interrupted, input-changed, and failed. Successful completion means the accepted manifest is readable, not merely that parsing finished.
- Cancellation prevents later acceptance from that job. Disconnecting a client does not cancel it. Restart keeps accepted artifacts, reconciles an already-published expected revision, and marks unfinished work interrupted. It never launches a new indexing, browser, build, or provider attempt automatically.
- Progress carries counts, phase, current bounded item information, diagnostics counts, and revision tokens. Graphs, source bundles, inventories, screenshots, and full diagnostic lists are fetched separately. Subscriptions and caches remain scoped to environment/project/physical checkout/application.
- Shared contracts and client-runtime behavior serve web, Electron, and mobile. All existing providers remain irrelevant to atlas indexing and capture; none needs a new capability or credential. Legacy provider analysis retains its existing support restrictions.

### 5. Real page captures from an attached application

- The MVP attaches to an already-running HTTP(S) application reachable from the selected environment. A private environment-local target profile contains its origin, deployment prefix, selected checkout/application binding, and optional session-profile binding. Users explicitly attach, edit, rebind, or detach it. Port discovery may suggest targets but cannot establish their source identity.
- Attaching does not prove that the process serves the indexed checkout. Default provenance is **user-confirmed target; running source not verified**. Capture details always preserve that distinction, the indexed generation, the observed target, and capture time. An optional independently verified build identity may strengthen provenance later; it is not a dependency of this MVP.
- A portable scenario has a stable ID, route ID, name, explicit parameter/query values or a relative target path, desktop/mobile viewport, light/dark theme, readiness condition, and expected navigation/HTTP outcome. Origin, private session material, machine paths, and secrets are environment-local. Users must not put secrets into portable query/fixture values; provide private per-environment substitutions for such values without saving them in Git.
- Create a default unconfigured scenario draft for a normal static route. For dynamic routes, require actual values and encode them according to segment type. Missing values, unsupported matching rules, or unknown deployment configuration yield **needs setup**, not a guessed URL. Resolve targets against the attached profile; do not bake client-local origins into portable documents or shipped bundles.
- Support direct navigation with a condition-based readiness assertion: visible text or a validated locator. Require that assertion before a capture can be labeled ready. Do not expose arbitrary JavaScript execution as scenario configuration, use fixed sleeps, or infer app readiness from network silence. Expected redirects or deliberate error responses must be named in the scenario; unexpected redirects/statuses remain distinct outcomes.
- Allow a private session profile imported from existing Playwright-compatible storage state through environment-owned setup. Anonymous scenarios need no profile. Profiles can be replaced and deleted; deleting one makes its scenarios need setup. Raw credentials/session state never enter portable artifacts, progress payloads, image metadata, or logs. Automated login flows and general workflow recording are outside this release.
- Implement a server-owned capture runner with Playwright and one lazily started Chromium process per active environment, isolated contexts per scenario, and capture concurrency of one. Close owned contexts on completion/cancellation, release the browser when the queue drains, and terminate only processes the runner started. Never drive or close a user's collaborative preview tab.
- Existing collaborative preview automation is desktop-client-hosted and thread-scoped. It does not establish server-side rendering capability for web/mobile-only or remote environments. Reuse compatible contracts/utilities, not that host assumption. Existing signed asset delivery is a reuse point; environment-owned browser capture is a new boundary.
- Expose capture capability and missing-browser/setup failures explicitly. Include a documented, explicit setup action for the pinned browser on supported server platforms, with no automatic downloads when Codebase opens. Validate one working packaged Windows desktop setup and one standalone server setup as release acceptance. Missing capture capability leaves indexing and browsing fully usable; it cannot be reported as successful rendering.
- A capture job binds the scenario revision, target-profile revision, indexed generation, and pre/post source fingerprints. Source/profile/scenario changes during capture prevent attachment as a current result. Keep an older accepted image visible as historical; show the newer failed attempt separately. Capture failure never destroys the atlas.
- Bound a requested batch to 20 scenarios and navigation/readiness work to 30 seconds per scenario. Capture one viewport, not an unbounded full page. Start with desktop 1440 × 900 and mobile 390 × 844 presets; expose custom sizes only within existing preview dimension limits. Store a bounded full image and a thumbnail, with at most 8 MiB per full image and 256 MiB of capture images per environment. Eviction is explicit in metadata and offers recapture. These are design limits subject to measured adjustment, not performance results.
- Terminal capture outcomes distinguish ready/captured, expected-redirect captured, expected-error captured, unexpected-redirect, HTTP failure, readiness failure, unreachable, unavailable, cancelled, interrupted, and input-changed. A normal completed page is not automatically classified as populated, empty, or authenticated; those are the scenario's declared state with its assertion evidence. Do not claim automatic detection of missing data or successful business behavior.
- Captures are point-in-time observations. Track source/configuration/scenario/profile changes and invalidate related image relevance conservatively; external data changes cannot be detected reliably and always require a new capture. Separate source-match state, scenario-match state, and capture time. Never collapse them into an unconditional “current page” badge.

### 6. Delivery, privacy, and client behavior

- Persist runtime captures, private target/session profiles, image IDs, job timestamps, and capture receipts in environment-local state/cache. Commit only source structure and reviewed user documentation/scenario definitions. A fresh clone opens the atlas and scenario definitions but shows captures as unavailable until captured in that environment.
- Extend environment-owned asset access with a capture-image resource scoped to project/checkout/application/capture identity. Authenticated clients request bounded expiring URLs or equivalent artifact handles through the selected environment's existing transport. Do not require a fake conversation thread or expose arbitrary local filesystem paths to make project-owned images accessible.
- Web, Electron, and mobile retrieve the same captures through authenticated environment routing, including relay/tunnel modes. A client device never receives a server-loopback URL as its image source. Cross-environment/project access, expired handles, and deleted captures fail explicitly. Renewing an expired handle must not trigger a new capture.
- Route cards lazy-load thumbnails for visible items. A scenario selector chooses the represented capture; detail opens an image with outcome/provenance, setup, capture, recapture, cancellation, and deletion controls. Do not create a live iframe or browser per route. General interactive embedding and reverse-proxying the application are outside this release.
- Keep the existing scoped graph renderer initially, with deterministic layout, grouping, and navigation. Ensure cycles, strongly connected modules, disconnected items, and isolated nodes remain visible. Large views use grouping/paging, not silent omission. A graph-library or general layout-engine replacement is not a prerequisite.
- Web/desktop provide the graph and route-card views; mobile provides equivalent native list/detail navigation, features, source references, scenario setup, and images. Preserve native window-control clearance, real viewport sizing, accessible labels/focus, and scrollable small-screen controls. No perpetual edge animations, force simulations, or continuous idle repaint.
- Document the shipped workflow for users, the extractor/evidence/contracts for contributors, setup/troubleshooting for operators, and the new vocabulary in the glossary. Product UI should explain the user's next action rather than source-module or test-harness details.

### 7. Migration and implementation order

- Keep existing accepted AI maps read-only and labeled **Legacy AI map**. Do not silently reinterpret, regenerate, delete, or migrate them into structural truth. Users can switch between legacy documentation and the atlas. Starting an explicit first index writes the new format; returning to a legacy view does not start paid work.
- For supported applications, make the source-derived atlas the default after its first accepted index. Unsupported routing configurations keep generic views and available legacy documentation. This MVP does not remove legacy provider adapters or rewrite their historical attempts.
- Build in five dependency-ordered slices within this one spec: contracts/artifact and job lifecycle; compiler extraction plus both route adapters; integrated scoped views and feature groups; attach/scenarios/capture/assets; cross-client/remote acceptance and documentation. Each slice must exercise the primary service boundary. Do not call the feature delivered before the capture workflow and user acceptance below pass.

## Testing Decisions

**Approved by the developer on 2026-10-27:** one primary feature integration seam through the existing Codebase service integration harness with real Git, SQLite, and compiler fixtures, plus one real Next application/Playwright acceptance flow proving page captures reach clients. Existing scoped RPC/asset and client harnesses verify their routing/interaction portions; they do not duplicate the full feature model. The developer explicitly approved this replacement's testing boundary; no further testing-seam confirmation is required before publication as ready-for-agent.

- **Test observable behavior.** Start a job as a client would, observe durable state, await accepted publication, read the atlas through the service, inspect portable output, and fetch captures through normal asset authorization. Assert routes, evidence, unknowns, revisions, and visible outcomes. Do not assert parser traversal order, private helper call counts, graph coordinates, generated prompt text, or screenshot byte identity across platforms.
- **Prefer the existing integration harness.** Extend its real temporary Git checkouts/worktrees, SQLite, Codebase service/store, revisions, subscriptions, and controlled worker execution. Use the real compiler and adapters for structural fixtures. Forbid provider execution in these tests: a successful atlas requires no analysis thread or provider session. Reuse the existing RPC harness for a focused typed dispatch check and asset-access tests for scoped delivery.
- **Synchronize explicitly.** Subscribe before dispatch, await durable job terminal events and drainable workers. Use test-only typed receipts if the accepted-atlas/capture milestones need them; production behavior must not depend on a test receipt bus. Use Deferred barriers for race/failure injection, never sleeps or polling for eventual completion. Browser acceptance waits on observable application assertions, with a timeout only as a failure bound.
- **Structural success fixture.** Create a small real Next App Router source fixture with a static page, parameterized page, nested/grouped layout, loading/error boundaries, component alias, re-export, type-only import, route handler, slot/interception declaration, unresolved computed import, and unsupported config. Assert exact expected structural facts and diagnostics independently authored for the fixture. Traverse from overview to a route to a component and its source without provider activity.
- **Dogfood adapter fixture.** A separate compact TanStack fixture covers pathless parents, index/dynamic/nested routes, directly declared route components, mismatching generated output, and computed options. Index T3's actual web application for a documented acceptance sample; compare representative known route declarations, not a hand-maintained inventory of every T3 route in unit tests.
- **Portability and fidelity.** Repeat scans and open committed artifacts in a second clone/environment without the original SQLite state; assert byte-identical structural content and stable IDs. Cover dirty/untracked source, line-ending normalization, a subdirectory project, multiple app roots, branch and detached-HEAD transitions, and a map-only commit. Ensure user groups/scenarios survive regeneration and removed targets remain visibly missing.
- **Freshness and publication failures.** Change a layout, component, compiler alias, package export, framework/configuration input, or destination revision during indexing. Assert correct stale/unknown state and rejection of late publication, retaining the prior generation. Inject write failure and a crash around the accepted-manifest switch; restart must reconcile an already accepted revision exactly once or retain interrupted state without automatic work.
- **Lifecycle and bounds.** Exercise duplicate command IDs, changed payloads, equivalent concurrent clients, queue bounds, cancellation, lost connections, restart, unsupported schemas, conflict markers, parse failures, overflow, and deterministic partial results. Validate every graph endpoint/evidence anchor and honest coverage counts. Include cycles/disconnected nodes so the existing presentation cannot lose them.
- **Capture service fixtures.** Most service scenarios may inject a deterministic capture adapter returning bounded image artifacts and explicit receipts to cover queueing, profile/scenario revisions, authorization, cancellation, cache eviction, and failure preservation. Those tests do not prove rendering. Test that credentials, private profile paths, target origins, capture timestamps, and image payloads are absent from portable structural artifacts as specified.
- **One real rendering acceptance fixture.** Build/run a small pinned Next fixture in disposable state with an actual server component, client interactivity, inherited layout, global style, dynamic parameter, and authenticated test-session fixture. Through the normal capture service, capture named populated, signed-out/expected-redirect, empty, and deliberate error scenarios using real Playwright. Assert expected visible DOM markers and image dimensions; inspect representative resulting images manually. A static mock server or injected PNG cannot substitute for this gate.
- **Complete client acceptance.** In one integrated primary-agent pass, index the fixture, inspect a route/component/evidence source, create and revise a feature group, attach the real fixture, configure a scenario, capture/enlarge its image, change source, observe outdated state, refresh/recapture, cancel another capture, and reconnect a second client. Verify web and Electron presentation plus native mobile list/detail equivalence through the project's existing client test workflows. Browser/computer use during implementation requires the developer's explicit agreement; this spec task starts none.
- **Remote behavior.** Repeat image retrieval and scenario actions from a client whose localhost is not the server, using the real environment connection/asset path.

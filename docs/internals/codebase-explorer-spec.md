# Codebase explorer with selectable AI and Git-versioned maps

## Problem Statement

Understanding a codebase requires repeatedly opening files, following imports, finding entry points, and asking an agent to explain how the pieces fit. A file tree shows where code lives but does not explain what each part does, how frontend and backend communicate, or how a user action reaches a particular function. Explanations in individual threads are difficult to revisit and share.

A diagram of every file, component, function, and connection would be unreadable and expensive to generate. A useful map must start with the application as a whole, then reveal more detail only where the user wants to explore. It must explain both the items and their relationships, identify missing analysis, and distinguish evidence from inference.

The map must describe the code the user is actually working on. A project can have several checkouts and worktrees, and the same working directory can change branches. Keeping the map only in an environment database or a global cache would separate it from the source it describes. Users also need to choose the providers and models doing the analysis using their existing T3 Code configuration and subscriptions.

## Solution

Add a project-level **Codebase** destination that opens a dedicated exploration workspace. The proposed default entry point is a sidebar item. The top-bar Chat / Codebase switch remains a documented alternative; final placement has not been explicitly selected by the developer. Both entry points resolve to the same project-and-checkout view rather than separate features.

The initial map shows the application's clients, services, storage, external systems, and technology stack. Selecting an item opens an inspector with a plain-language explanation, its responsibilities, source references, and incoming and outgoing relationships. Selecting a connection explains its direction, meaning, mechanism, and supporting evidence.

Double-clicking an expandable item, choosing Explore from its context menu, or pressing its visible Explore button moves into that scope. For example: application overview, frontend routes and modules, a route's components, then a component's functions and effects. Breadcrumbs and Back return to previous scopes without discarding the user's place. The hierarchy follows the application's structure; it is not restricted to four universal layers.

If the next layer has not been built, show the proposed scope, selected AI, and an explicit **Build this layer** action. Analysis operates in bounded passes. Existing maps remain usable while another pass runs. Opening, panning, inspecting, or returning to a map never starts paid provider work by itself.

An **AI setup** control beside analysis actions reuses the chat provider/model selection experience. Users choose a default analyzer, optionally use different selections for overview and detail passes, and override the choice for an individual run. Each accepted result records the provider, model, and supported options that produced it. The initial implementation runs one analyzer per pass; selecting several AIs means selecting different AIs for different passes, not automatically running an ensemble.

Store accepted maps as readable, versioned JSON within the selected project's Git working tree: one small manifest and separate documents for independently explored scopes. The files can be reviewed, committed, merged, and checked out with the source. Runtime execution state stays in T3 home. Checking out a branch loads that branch's map files; entering another worktree loads that worktree's files. No map generation, branch switch, staging, commit, or push happens merely because a user opens Codebase.

## Implementation Decisions

### Product ownership and navigation

- **Scope the view to an environment, project, and resolved checkout.** Use the existing thread workspace resolver for entry from a thread: an assigned worktree takes precedence over the project's workspace root. Project entry defaults to its main checkout and allows choosing existing project worktrees. A draft referring to an unprovisioned worktree is not an existing checkout; show that state rather than generating in the main checkout.
- **Use physical checkout identity for runtime work.** Resolve canonical paths with existing workspace/VCS services. Branch names, project titles, remote URLs, and repository grouping identities are not sufficient execution identities. Separate clones and worktrees remain separate even at the same commit. A branch change in one physical directory changes its content, not its identity.
- **Keep navigation reversible.** The map owns a breadcrumb history, selection, and viewport per scope. Chat remains available. Do not create provider work on navigation, and do not require a normal conversation to exist. Entry from sidebar, chat header, command palette, or a configurable keybinding must resolve the same view and checkout. Settings contains defaults and links to provider configuration, not a separate explorer implementation.
- **Treat the layout as a presentation choice.** The sidebar destination is the proposed implementation default, with a full-workspace map and optional inspector. The top-toggle mockup remains a design alternative. A compact outline/detail presentation supplies equivalent mobile behavior; double-click and right-click are shortcuts rather than requirements.

### AI selection and reuse of chat execution

- **Reuse the configured provider instance catalog and model option descriptors.** Do not hardcode provider accounts, model names, reasoning levels, or a new hosted-model API. The effective runtime selection uses the existing `ModelSelection` concept, including the environment-local instance and validated option selections.
- **Use a small inheritance model.** AI setup exposes a default analyzer and optional Overview and Detail overrides. A run-specific override wins, followed by the pass-kind override, followed by the project analyzer default. If no analyzer default exists, seed the first selection from the project's chat default and show it for confirmation in the Build action. Selection is frozen when the run is accepted; changing defaults affects later runs.
- **Separate portable preference from local account binding.** Versioned preferences may contain driver kind, model identifier, and supported option values. The mapping to a configured provider instance belongs to that environment's runtime settings. If several instances match, reuse a valid explicit local binding or require a selection. Missing instances, models, or options require a visible correction; do not silently downgrade or fall back. Authentication secrets, account identifiers, resume cursors, and machine-specific configuration never enter the map JSON.
- **Run one analyzer for each pass.** Users can select different AIs for overview and deeper scopes or retry with another AI. Automatic reviewer agents, voting, and concurrent multi-model analysis are outside this implementation. No new model or provider dependency is required.
- **Represent an analysis attempt through the existing durable thread/turn machinery.** Create a dedicated analysis-purpose thread for a run, with typed metadata identifying the project, checkout, scope, pass kind, request ID, and input fingerprint. Keep it separate from the user's active conversation and expose it through Analysis activity and View transcript. Existing threads default to conversation purpose; analysis threads must not pollute normal thread lists, unread counts, or unrelated notifications. Retry creates a new attempt while preserving the previous attempt's history.
- **Dispatch through the normal pipeline.** Analysis start flows through typed orchestration commands, the engine and pure decider, the provider command reactor, the provider service, and the existing adapter registry. Output returns through normal runtime ingestion and durable thread state. Reuse model switching or session restart behavior, approvals, user input, interruption, streaming, and usage reporting where available. Do not spawn provider subprocesses in a new analysis service, call provider SDKs from clients, or route analysis through the lightweight thread-title/commit-message text-generation helper.
- **Keep adapter-specific behavior at the boundary.** Codex, Claude, Cursor, Grok, and OpenCode are all candidates for the same pass contract. Structured JSON in the normalized final assistant result is the baseline; native schema output can be used when supported but is not required. Each adapter needs an explicit capability and acceptance decision for workspace reading, final-result extraction, cancellation, and analysis permissions. An unsupported combination is disabled with a reason, not silently mapped to another provider.
- **Treat analysis as inspection.** Request read-only workspace inspection using existing sandbox and approval controls. The server publishes accepted map files; the agent is not asked to edit source or write authoritative map files. A prompt alone is not a read-only guarantee. Where the current adapter cannot enforce the required behavior, implement the narrow capability at that boundary or report analysis as unsupported until it can. Analysis does not grant automatic execution of project scripts, network commands, or source edits.

### Bounded passes and graph meaning

- **Begin with deterministic workspace inventory, then AI explanation.** Enumerate relevant project files and recognized project metadata through existing workspace/VCS services. Respect repository ignore rules and exclude dependency directories, generated build output, binaries, runtime state, and map artifacts themselves. Supply a bounded inventory, selected source, existing parent summary, and output schema to the chosen agent. Do not feed the entire repository into every pass.
- **Map one immediate scope at a time.** Overview produces major systems and stack relationships. Expanding one system produces its immediate routes/modules; later passes produce components, symbols, and effects as appropriate. A backend-only, native, or library project uses its own meaningful boundaries. Layer numbers describe navigation depth rather than a universal code taxonomy.
- **Make limits explicit in contracts.** Bound source input, output bytes, node/edge counts, and individual summaries. Oversized scopes become grouped child scopes and record omissions or truncation. Do not silently truncate JSON and accept it. Set initial numeric budgets against representative fixtures and the existing provider input limits before enabling generation; cover these limits in focused tests.
- **Give nodes stable identity and useful content.** A node has an ID, kind, display name, short responsibility, fuller explanation, source anchors, technology metadata where supported, and an optional child-scope identity. Function details can include inputs, outputs, callers, callees, and side effects when supported by evidence. IDs derive from normalized relative source anchors and qualified symbols or persistent synthetic scope keys, never labels or provider prose alone. Renames can change identity unless a reliable correspondence is established.
- **Represent relationships explicitly.** An edge has its own identity, endpoints, direction, relationship kind, concise label, explanation, and evidence. Imports, renders, calls, requests, events, reads, and writes are distinct relationship kinds. Cross-scope endpoints use resolvable boundary references; clients can display a boundary stub and navigate to its owning scope without loading the complete graph.
- **Do not equate a citation with proof.** Preserve referenced source ranges or symbols and their content fingerprints. A valid path proves a reference exists, not that an AI's interpretation is correct. Use source-backed and inferred states, describe the evidence, and reserve stronger verification claims for deterministic checks that actually establish them. Unsupported or dynamic behavior remains uncertain. Percentages must measure a declared inventory, never imply every behavior or runtime connection is understood.

### Git-owned JSON and local runtime state

The accepted artifact is a collection of ordinary JSON documents under a dedicated, trackable directory inside the selected project root. It is not stored in the ignored development-runtime directory, the Git administrative directory, or only in T3 home. For projects rooted below a repository root, keep a project-relative namespace that resolves to the corresponding project location in each worktree. Two runtime project records pointing at the same on-disk project namespace read the same artifacts; they must not create incompatible copies keyed by environment-local project IDs.

| Logical document or state | Contents and ownership                                                                                                                                                                                                             |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Project manifest          | Schema version, portable project-relative identity, root scope identity, analysis configuration, and portable analyzer preferences. Small, human-readable, and versioned with the source.                                          |
| Scope document            | One complete accepted scope: stable nodes, relationships, child-scope descriptors, coverage/omissions, source anchors and fingerprints, prompt/schema version, and producing provider/model/options. Versioned with the source.    |
| Analysis attempt          | Actual environment-local provider instance, run/thread/turn references, command deduplication, activity, approval state, cancellation, diagnostics, and any unaccepted candidate. Durable runtime state in the owning environment. |
| Client view state         | Breadcrumb history, selected item, viewport, and inspector presentation. Local to the client and checkout; not committed graph content.                                                                                            |

- **Use one scope file as the acceptance unit.** Expanding a child creates or replaces its own document. Parent documents already contain stable child-scope references; whether a child has been built is resolved from the available documents rather than maintained by rewriting every ancestor or a giant global index. Manifest changes are independent configuration changes. A manifest without a root document is an unbuilt map, not a partially accepted graph.
- **Keep the schema portable and strict.** File references use normalized project-relative paths; reject traversal, escapes through symlinks, duplicate IDs, invalid endpoints, incompatible versions, and malformed references. Do not persist absolute checkout paths, environment IDs, thread IDs, provider session IDs, credentials, full prompts, or raw transcripts in portable documents. Production diagnostics and analysis history can link to local runtime records without making those records necessary to open the map elsewhere.
- **Make diffs useful.** Serialize deterministically with stable key/collection ordering and human-readable formatting. Avoid rewriting unrelated scopes or changing timestamps solely because the map was opened. If a regenerated accepted scope has no meaningful change, retain its file and record the attempt in runtime activity instead of creating metadata-only churn.
- **Treat disk as the source of truth for accepted content.** The environment may cache decoded scopes or maintain a rebuildable index, but it must invalidate them on artifact changes, checkout changes, explicit refresh, and reconnect reconciliation. Replaying old orchestration events must never recreate or overwrite map files removed by a checkout or user edit. A clone containing only committed source and map documents must support read-only exploration without access to the original environment database or an AI account.
- **Keep normal Git semantics.** Generated files appear as untracked or modified files until the user stages and commits them. Uncommitted files can survive a branch switch according to Git's normal rules; the UI must not promise that they are versioned before commit. Never auto-stage, commit, push, force-checkout, edit ignore rules, or copy a map between worktrees. If ignore rules exclude the artifact location, explain that Git will not carry it until the user resolves the exclusion.
- **Handle malformed files without destructive recovery.** Missing scope documents are unbuilt; invalid JSON, merge conflict markers, unsupported newer schemas, and inaccessible files have distinct states. Preserve the bytes on disk, show the affected scope, and offer retry/reload or source-control recovery. Schema migrations are explicit, validated file changes that produce reviewable diffs. Do not silently regenerate over hand edits. Parent refreshes can make old child files unreachable; do not delete those files automatically in the first release.

### Freshness, publishing, and concurrency

- **Fingerprint relevant source, not only HEAD.** Record the analyzed source inventory and content digests, including relevant dirty tracked files and nonignored untracked source. Include configuration and dependency manifests that affect interpretation. Exclude graph artifacts and runtime output from the source fingerprint. Commit and branch metadata provide provenance, but a commit containing only map updates must not invalidate unchanged source.
- **Track freshness separately from coverage and job progress.** A scope can be built but stale, current but only partially explored, or readable while a refresh fails. Missing, inaccessible, conflicted, and unknown-freshness states must not appear as current. A targeted refresh updates that scope; it must not claim that all descendants were rebuilt. Changes to shared source or analysis configuration conservatively invalidate dependent scopes where the relationship is known and mark freshness unknown where it is not.
- **Bind every run to its inputs.** Capture the resolved checkout, actual Git state, source fingerprint, parent/scope identity, configuration, and current destination revision before dispatch. Preserve that binding for the entire attempt. Observe workspace changes and recheck inputs immediately before accepting the result. If relevant source, checkout state, configuration, or destination changed, keep the result as an unaccepted candidate and show that the inputs changed; offer a fresh run rather than overwriting newer content.
- **Validate before saving.** On a successfully completed provider turn, extract the designated final JSON result, decode its schema, enforce limits and referential integrity, validate source anchors, and reconcile server-owned identities and provenance. Partial streamed JSON is activity, not a map. Invalid output does not replace the last accepted scope and does not trigger an unbounded automatic repair loop. Retry is explicit.
- **Publish with compare-and-swap and atomic replacement.** Serialize writers for the physical artifact namespace and compare the destination's current content revision with the run's expected revision. Write a temporary candidate on the same filesystem and atomically replace the scope document only after validation and freshness checks. Readers see the previous complete scope or the next complete scope. Configuration writes use the same revision checks. Do not mistake an in-process queue for protection against another environment or editor: use a filesystem lock for cooperating T3 writers and recheck external revisions. A stale lock must be recoverable without killing arbitrary processes.
- **Acknowledge external Git races.** Coordinate T3-initiated checkout mutations with artifact publication. Uncoordinated external Git/editor operations cannot be made transactional merely by taking a T3 lock. Revalidate observed filesystem/Git generations and invalidate promptly if they change; do not report the result as current or roll back the user's files to hide the race. Include explicit branch-switch and destination-edit conflict tests.
- **Keep the default scheduler small.** Allow one active analysis pass per physical project checkout, with later requests queued. Repeat requests carrying the same command ID are idempotent; requests for an already active identical scope/input can attach to that run. Different worktrees can run independently subject to existing provider limits. A refresh or deletion of a source thread must not accidentally cancel a separate analysis attempt.
- **Model cancellation and restart honestly.** Separate queued, running, waiting for approval/input, validating, saving, succeeded, failed, cancelled, and input-changed outcomes. Cancel routes to the existing provider interruption path and prevents an unaccepted late result from publishing. Atomic acceptance is the completion boundary; cancellation after acceptance reports the completed result instead of claiming to undo it. On server restart, reconcile durable attempts with existing provider sessions and on-disk accepted revisions; never start another paid pass automatically or leave an orphaned permanent spinner.
- **Do not confuse completion signals.** Provider turn completion, checkpoint completion, and accepted-map publication are different milestones. Only validated, durably saved JSON makes a map pass successful. Production coordination uses persisted events and worker state. Runtime receipts are test-only synchronization and must not become a production dependency. An artifact write followed by a crash before the success event is reconciled idempotently from its recorded acceptance identity/revision; it must not generate a second result.

### Module boundaries and wire behavior

- **Contracts:** add schemas for the portable manifest, scope/node/edge/evidence documents, analysis request/result states, checkout-scoped identities, revision tokens, errors, and bounded RPC responses. Extend existing orchestration schemas with analysis purpose/metadata and the minimal run intent/outcome events required for durable coordination. Keep schema modules free of filesystem and orchestration runtime work.
- **Server:** introduce one bounded Codebase service with an artifact-store boundary and a drainable analysis worker/reactor. Reuse workspace resolution, filesystem access, VCS status, provider selection, orchestration dispatch, and runtime ingestion. Keep the pure decider free of file reads and provider calls. The store owns decoding, freshness checks, compare-and-swap, and publication; the worker owns pass preparation and acceptance of normalized provider output.
- **Typed operations:** expose overview/scope reads, AI configuration read/update, analysis start/status/subscription, cancellation, and freshness refresh. Requests identify environment-local project/checkout, scope, pass kind, expected artifact revision, and explicit model override when present. Start returns a durable run identity; clients subscribe to bounded progress and terminal outcomes. A source-freshness refresh is a read/invalidation operation; AI regeneration requires an explicit start request.
- **Shared client runtime:** own environment-scoped queries, model preference resolution, run subscriptions, invalidation, reconnect recovery, and command deduplication. Cache by environment, project namespace, resolved checkout, scope, and artifact revision. Never mix state from identically named projects or branches on different environments.
- **Clients:** web renders the graph and inspector; desktop uses that shared web surface and existing native source-opening capabilities. Mobile uses shared state with native navigation, tap-to-inspect, explicit Explore, and a compact map or outline. When a native editor cannot open a remote reference, provide the existing environment-backed source-reading path. Availability and limitations must be visible per client rather than relying on Electron-only behavior.
- **Transport and permissions:** serve files and execute providers only on the owning environment through the authenticated RPC boundary. Existing project authorization applies to reads and analysis writes. Browser clients never read local project files directly or use a baked-in local server origin. Local, relay, tunnel, and hosted-web connections use the same contracts. Subscriptions deliver scope revisions and compact progress, not the entire repository graph or raw provider transcript on every update.
- **Rendering and performance:** fetch the overview first and child scopes only when opened. Use stable cached layouts, bounded node counts, viewport culling where useful, and selected-scope detail requests. Keep graph layout separate from the persisted semantic graph. Avoid perpetual force-layout simulation, animated edges, or continuously repainting status indicators. Reuse existing UI primitives; selection of a new graph/layout dependency requires a separate explicit decision.
- **Documentation:** user documentation explains navigation, AI choices, passes, Git-owned maps, freshness, and recovery in shipped-product language. Internals explain schema ownership, analysis-purpose turns, acceptance, and invalidation. Add scope, pass, and accepted map vocabulary to the glossary. Operational troubleshooting belongs with runbooks, not in product controls.

### Implementation order and acceptance gates

1. Define portable document contracts, checkout resolution, and the artifact-store acceptance behavior. Demonstrate loading a committed map in a fresh environment and distinct map content in two real worktrees.
2. Add the read-only explorer using fixture JSON: overview, selected-node/edge details, child scopes, breadcrumbs, source references, and mobile equivalents. Keep a clear distinction between fixtures and generated maps.
3. Wire AI setup and one overview pass through the real chat orchestration pipeline. Demonstrate that the selected provider instance/model/options reach the adapter and that only valid output becomes a saved root scope.
4. Add detail passes, per-pass overrides, scoped refresh, cancellation, duplicate-request handling, input-change conflicts, restart/reconnect recovery, and artifact watching. Exercise these at the approved integration boundary.
5. Run the approved real-provider and client acceptance stories, document unsupported adapter capabilities explicitly, and publish user documentation. Completion requires the whole source-to-map-to-deeper-scope workflow, not merely a working graph renderer or a fixture that parses.

## Testing Decisions

The developer approved the following boundaries on 2026-10-25: one primary integration boundary through normal orchestration using a deterministic provider adapter and a real temporary Git repository/worktrees, focused UI interaction checks, and a separate real-provider acceptance pass.

- **Test observable behavior.** A good test requests a pass as the client would, observes durable run progress, waits for explicit completion, reads the resulting map, and inspects the JSON actually on disk. Do not assert private helper call counts, graph library internals, prompt wording, or every implementation method. Preserve one primary end-to-end analysis fixture instead of duplicating this workflow at every layer.
- **Extend the existing orchestration integration harness.** Reuse its temporary filesystem and Git repository, real SQLite persistence, engine/projections, provider service, checkpointing, and deterministic TestProviderAdapter. Extend the fixture with the Codebase service/worker and a scoped subscription. Exercise the new RPC's routing with the existing server RPC harness, while keeping the substantive generation/storage scenarios in the primary integration harness.
- **Synchronize without timing guesses.** Subscribe before dispatch, await relevant persisted events or test-only typed receipts, and drain the workers that perform follow-up work. Add an artifact-accepted or analysis-settled test receipt if the existing receipts cannot identify that milestone. Production must not subscribe to test receipts. Existing older polling helpers are prior art for setup only, not patterns to copy into new analysis tests. Use controlled barriers for races, not sleeps.
- **Cover the main success story.** Configure provider/model/options; build the overview; expand frontend and a component; inspect a connection and a source anchor; verify the expected individual JSON documents; reconnect a second client; reopen the map in a fresh environment without the original runtime database. Assert explicit coverage, provenance, and accepted revision.
- **Cover provider routing at the adapter seam.** Parameterize supported driver kinds through the same deterministic fixture to verify explicit instance routing, inherited and overridden model options, unsupported capability errors, approval/input handling, interrupted output, and normalization of the final result. Do not treat parameterizing a fake adapter as live validation of all five providers.
- **Cover actual Git behavior.** Use two worktrees, two branches, detached HEAD, dirty tracked source, untracked source, a source-only commit, and a map-only commit. Test that map-only commits remain fresh, branch switches read branch-local files, a branch with no map is unbuilt, and an in-flight analysis cannot overwrite a detected new checkout/destination revision. Include a project in a repository subdirectory and multiple runtime project records addressing the same artifact namespace.
- **Cover publication and corruption.** Reject malformed/oversized JSON, duplicate IDs, dangling endpoints, invalid source paths/ranges, unsupported versions, and conflict markers. Inject write failure and failure between replacement and success-event persistence. Assert preservation of the previous accepted document, idempotent reconciliation, deterministic diffs, and no torn-file reads. Test hand edits and two cooperating writers using explicit barriers.
- **Cover lifecycle and remote reuse.** Duplicate starts attach or queue without duplicate provider invocations; cancellation suppresses late acceptance; a disconnected client does not cancel work; a new client sees the existing run; server restart resolves attempts honestly. Assert that environment/project/checkout subscriptions never expose another workspace and that reconnect uses the current accepted artifact revision.
- **Keep focused contract checks where they add value.** Schema round trips, older supported versions, portable preference decoding, and invalid document cases can use the existing contract-schema test style. Workspace file/path tests and VCS config tests are prior art for containment, relative paths, and on-disk configuration. Avoid a second model implementation embedded in the tests.
- **Verify UI interactions and entry-point parity.** Select nodes and edges; Explore by button, keyboard, double-click, and context menu where available; return through breadcrumbs; change AI defaults and overrides; handle unbuilt, stale, conflict, failure, cancellation, and unavailable-provider states. Check sidebar/header entry, command palette/keybinding routing, returning to Chat, worktree switching, remote source references, and mobile equivalents. Use stable semantic locators and the project's existing client test workflows during implementation.
- **Separate live acceptance from fixtures.** With an explicitly selected configured provider, generate a real repository overview and at least one detail layer, verify representative source-backed relationships manually, inspect the Git diff, cancel a real run, and reopen the committed map on a second environment. Repeat a smoke workflow for every adapter advertised as supported. Record the exact provider/model/options, source revision, supported clients, and remaining gaps; fixture success alone is insufficient.
- **Measure the relevant performance boundary.** Use a representative large repository and bounded scopes to verify that opening the overview does not send all descendants, inspecting a node does not trigger analysis, updates do not rebroadcast entire maps, idle rendering does not continuously repaint, and worktree switches invalidate the correct cache. Keep tests scoped to the changed behavior; CI owns repository-wide checks.

## Out of Scope

- Implementing or releasing the feature as part of this specification change.
- A complete file/function graph generated in a single pass or a claim that all static and runtime behavior can be discovered automatically.
- Automatic analysis on every edit, navigation, branch switch, or provider-settings change.
- A new model vendor, model-serving service, provider harness, embedding service, vector database, or graph database.
- Agent ensembles, automatic reviewers, parallel scope generation within one checkout, or autonomous repeated repair attempts.
- A diagram-authoring application, free-form graph editing, or a new general source-code editor.
- Runtime tracing, production telemetry, execution profiling, or proof that inferred behavior occurs at runtime.
- Automatically changing source to match the map, or changing the application's architecture on the user's behalf.
- Automatic Git staging, commits, pushes, branch creation, worktree provisioning, conflict resolution, or garbage collection of unreachable scope files.
- Cross-repository federation, a central cloud map service, or live merging of edits made in unrelated clones.
- Requiring a local filesystem or provider credentials on a remote browser/mobile client.
- New non-Git version-control implementations. Non-Git projects may display a clear unsupported-generation state in the first release rather than implying Git versioning is available.
- Treating the exploratory mockup, deterministic provider fixture, or first adapter smoke test as complete cross-client and cross-provider acceptance.

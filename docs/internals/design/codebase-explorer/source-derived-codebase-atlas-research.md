# Source-derived Codebase Atlas: research and migration proposal

Date: **2026-10-27**. Status: research only; existing spec unchanged. Repository evidence refers to the inspected working tree at `e57bc809b2cec815f678d1c6a279cd5097ab5de3`, including existing uncommitted Explorer changes. **Verified** describes inspected source/documentation; **Proposal** describes future behavior; **Unknown** identifies unproved relationships or compatibility.

## Recommendation and guarantee boundary

**Proposal:** replace AI-authored structural maps with a source-derived atlas: deterministic syntax/symbol/import facts, framework route composition, and separately captured runtime scenarios. Optional AI explains existing fact IDs; it cannot create structural nodes or edges. Opening and indexing need no provider credentials. Business features remain user-authored labels or explicitly inferred suggestions.

**Verified:** TypeScript exposes syntax trees and symbol/type analysis; React rendering executes components before committing DOM changes. These are different evidence layers, not interchangeable representations. ([Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API#type-checker-apis), [React rendering](https://react.dev/learn/render-and-commit))

**Conclusion from those contracts:** visual blocks can faithfully summarize recognized source constructs without AI. They cannot guarantee every runtime behavior or business feature. A reversible block language is a separate editor project: it must represent arbitrary expressions/control flow and preserve source details and edit semantics. An architecture projection deliberately drops detail; it should navigate back to source, not promise round-trip code generation.

**Faithful previews of arbitrary Next pages cannot be guaranteed by static translation alone.** Next orchestrates Server Components, RSC payloads, prerendering, and client hydration. Static exports can avoid a continuously running Next server for supported apps, but still execute a build and exclude request-dependent functionality. Importing a page into a generic React canvas is not equivalent. An already-running app can be attached without launching another instance. ([Next rendering](https://nextjs.org/docs/app/getting-started/server-and-client-components), [static export limits](https://nextjs.org/docs/app/guides/static-exports#unsupported-features))

## Extraction model and honest limits

**Proposal:** retain distinct relationships: `imports` (including type-only), `declares`, `references-symbol`, `jsx-uses`, `layout-wraps`, `call-site-target`, `http-target-pattern`, and `observed-request`. Import declarations and function calls are separate language constructs; an import edge does not establish a particular call. A resolved call-site target does not prove execution. JSX composition is not the DOM tree. Runtime observations carry scenario/run/build identity and time; absence of an observation proves no absence of behavior. ([ECMAScript imports](https://tc39.es/ecma262/multipage/ecmascript-language-scripts-and-modules.html#sec-imports), [calls](https://tc39.es/ecma262/multipage/ecmascript-language-expressions.html#sec-function-calls), [React commitment](https://react.dev/learn/render-and-commit))

Use explicit evidence kinds: `syntax`, `symbol-resolution`, `framework-rule`, `build-observed`, and `runtime-observed`. Keep `user-authored`/`inferred` annotations separate. Ambiguous targets remain candidates with diagnostics, not asserted runtime calls.

Use compiler resolution with each package's effective tsconfig, project references, package exports/conditions, and workspace context. Record resolver mode and whether a target is source or a declaration file. TypeScript resolution models configuration, not every bundler behavior: `paths` does not rewrite emitted imports. ([module resolution](https://www.typescriptlang.org/docs/handbook/modules/reference.html#paths), [project references](https://www.typescriptlang.org/docs/handbook/project-references.html))

**Proposal:** computed imports, plugin loaders, dynamic component registries, callbacks/dispatch, unavailable dependencies, parse errors, and unsupported languages produce explicit unresolved records. Never substitute guessed edges. Track generated files separately, including producer/version when known; do not execute generators during indexing. Unsupported repositories still get inventory/package/file views with coverage denominators. “Entire codebase” means accounted-for source and visible gaps, not a complete execution graph.

## Runtime previews and delivery — proposal

Run the real application in the **selected environment**, through an explicit launch/attach profile. Preserve its actual providers, global styles/fonts/assets, server/client boundaries, environment requirements, and data setup. Next's client boundary propagates through its module graph, while server-rendered children may cross it; a file-local directive badge alone is insufficient. ([boundaries/providers](https://nextjs.org/docs/app/getting-started/server-and-client-components), [CSS](https://nextjs.org/docs/app/getting-started/css))

A scenario defines route ID, concrete params/query, locale, viewport, theme, auth profile, fixtures, navigation entry/steps, and an observable readiness assertion. Capture success, redirect, auth-blocked, missing-data, timeout, or error explicitly. Loading/error/empty states require fixtures or deliberate interactions. Use a bounded reusable browser pool and isolated contexts, not a browser/iframe per route. Playwright provides condition-based assertions; no fixed sleep establishes readiness. ([assertions](https://playwright.dev/docs/test-assertions), [contexts](https://playwright.dev/docs/api/class-browsercontext))

Storybook is an optional source of authored isolated states, not a substitute for the app runtime. Its Next RSC support is experimental; server resources require mocks. Mark captures `isolated-story`, `mocked-app`, or `real-app` and record fixture versions. ([RSC limitations](https://storybook.js.org/docs/get-started/frameworks/nextjs-vite#react-server-components-rsc))

Keep screenshots, traces, auth storage, and raw network payloads in transient private environment storage; commit only portable, reviewed scenario metadata and sanitized evidence. Playwright explicitly warns that stored auth can impersonate accounts. ([auth](https://playwright.dev/docs/auth)) Provide deletion/recapture, retention limits, and expiring authenticated artifact handles.

For web/Electron/mobile and local/relay/tunnel, capture belongs beside the selected environment's app. `localhost` resolves to loopback, so a client browser's localhost is its own host; do not distribute environment-local origins as preview links. ([RFC 6761 §6.3](https://www.rfc-editor.org/rfc/rfc6761#section-6.3)) Extend authenticated environment transport for paged metadata and on-demand artifact bytes; do not assume a generic interactive reverse proxy already exists. Shared environment atoms are the reusable seam. ([atoms](../../../../packages/client-runtime/src/state/codebase.ts#L126-L170)) Mobile should retain native list/detail navigation and thumbnail/scenario inspection; desktop/web share scoped cards and source inspection. Interactive remote embedding needs a separate cookie/origin/WebSocket design.

## Bounded vertical slice and phased migration — proposal

1. **Parser-first:** one explicitly selected JS/TS app root, Next App Router conventions first because they expose page/layout composition directly. Produce route catalog, layouts/boundaries, imports, exported symbols, JSX use, unknowns, and source links without credentials, executing config, launching apps, or screenshots. Classify advanced slots/interception/config even when not fully supported. Use current scoped graph and mobile detail views.
2. **Dogfood before replacement:** add Pages Router and TanStack adapters. Include Pages [build-time `getStaticProps`](https://nextjs.org/docs/pages/api-reference/functions/get-static-props) and [legacy `getInitialProps`](https://nextjs.org/docs/pages/api-reference/functions/get-initial-props) as data-hook declarations. TanStack must understand pathless/flat/nested routes, route options and generated-tree correspondence; use source declarations plus freshness-checked generated output. Its documented file routing differs from Next. ([TanStack](https://tanstack.com/router/latest/docs/routing/file-based-routing))
3. **Runtime evidence:** explicit Next launch/attach profiles, named Playwright scenarios, thumbnails; optional public build-adapter export and existing Storybook stories. Add endpoint/data adapters only with dedicated evidence fixtures.
4. **Optional explanations:** a separate annotation RPC accepts existing fact IDs, text, citations, and provenance; its server validator rejects structural fields and unknown IDs. Keep v1 maps readable as legacy AI analysis; explicit rebuild publishes a versioned atlas, preserving old artifacts for Git recovery.

Retain checkout binding, fingerprints, revision checks, cancellation, and recovery. Add extractor/schema/framework versions and effective tsconfig/config/workspace/lockfile inputs to invalidation. Reparse changed files; invalidate reverse dependents and inherited layouts; configuration/resolution changes can invalidate the whole app. Watchers are hints, not freshness proof. Stable IDs should hash app-relative semantic keys, excluding absolute paths, timestamps, and line offsets; renames may create new IDs.

Publish immutable bounded shards followed by one locked atomic manifest-pointer replacement, with pre/post source checks. Restart exposes the last accepted generation and an interrupted job, never an automatic runtime launch. Keep discovery progress compact and graph detail paged. Existing limits are 80 nodes/200 edges per graph, 512 KiB documents, 50-file pages, 20,000 inventory files, and a 32 MiB index; treat them as starting budgets, with explicit partial status at limits. ([limits](../../../../packages/contracts/src/codebase.ts#L7-L17), [paging](../../../../apps/server/src/codebase/CodebaseIndex.ts#L367-L415)) Avoid a whole-repository graph payload, synchronous whole-monorepo typechecking, or continuous force animation.

### Proposed spec changes, acceptance, and open questions

Amend the [existing spec](../../codebase-explorer-spec.md#L94-L103) through a separate reviewed change: replace mandatory analyzer selection/analysis threads with indexing jobs; introduce typed evidence and extractor provenance; separate indexing/build/scenario coverage; replace “Build layer” with indexed drill-down; specify previews and annotation lifecycle. Update contracts/server/shared atoms/web/Electron/mobile together. This research changes none of those files.

Acceptance targets, **not measured results**:

- Two scans of identical source/config/tool versions produce byte-identical portable structure and stable IDs; no provider calls or app execution.
- Fixture suites assert exact route/layout/slot/boundary outputs for the rules above; every supported declaration has evidence, every unsupported case a reason. No import becomes a call or JSX becomes observed DOM.
- Editing a layout/alias/package export, deleting a file, switching worktrees, or changing source during publication produces correct invalidation/conflict; cancellation/restart retains the previous accepted generation.
- One dynamic authenticated route has named success, signed-out, empty, and error scenarios; hard versus intercepted soft navigation is distinguished. Failed capture never appears as a successful preview.
- Web, Electron, mobile, and remote-environment checks retrieve the same revision/evidence; auth and screenshots are absent from portable Git artifacts.
- Measure cold/warm scan time, peak memory, files reparsed, payload bytes, and client frame behavior on named fixture sizes. Enforce the declared paging/document caps; agree latency/memory budgets after measurement. No benchmark was run here.

**Open product decisions:** supported Next/compiler version matrix; default scan roots and generated-code policy; attaching versus starting apps; ownership of scenario fixtures/test accounts; screenshot retention/sharing; whether “features” means authored capabilities or proposed labels. **Unknown:** actual parser/ELK performance, native packaging/browser availability, deployment-adapter coexistence, and fidelity for any target application. Arbitrary runtime state and business semantics remain outside deterministic completeness.
